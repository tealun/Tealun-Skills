# Tasker 技能介绍

> **一句话定位**：Tasker 是 AI 代理的「执行纪律教练」——它不帮你写更多代码，但确保你写的每一行都经过验证、可追溯、不幻觉。

---

## 一、它是干嘛的？

Tasker 是一个**通用工作流纪律框架**，为 AI 代理的单任务执行提供：

- **结构化流程**：`intake → clarify → plan → confirm → execute → verify → close` 七阶段状态机
- **风险分级**：S/M/L 三级任务自动分级，含上下文修正
- **执行硬约束**：5 条不可违反的执行规则（禁止模拟、禁止提前宣称完成、必须验证等）
- **时间预算**：每步超时 + 总轮次上限，防止无限执行
- **失败回退**：执行失败自动回退到计划阶段，3 次回退后升级并请求人工介入
- **不满处理**：用户不满自动分类根因，同一会话重复问题自动应用防护

**它不是**：
- ❌ 多代理编排系统（如 swarm-coding）
- ❌ 具体工具（如爬虫、报表生成器）
- ❌ 自动化调度器（如 cron）

**它是**：
- ✅ 任何单任务的「执行纪律层」——无论你在写代码、查日志、写文档还是做分析

---

## 二、有什么优势？

### vs 无框架的裸执行

| 维度 | 裸执行 | Tasker |
|------|--------|--------|
| 幻觉风险 | 高（代理可能编造结果） | **极低**（Zero-Tool Zero-Progress） |
| 提前宣称完成 | 常见（"已修复"但没改文件） | **禁止**（Pre-Tool Completion Ban） |
| 验证 | 随机/无 | **强制**（PTV + Tool-Call Audit） |
| 失败处理 | 卡住或静默失败 | **自动回退**（Retreat + Retry Cap） |
| 时间控制 | 无 | **有预算**（Step Timeout + Total Budget） |
| 用户不满 | 重复犯错 | **根因追踪**（自动改进后续任务） |

### vs 其他技能框架

| 对比 | 其他技能 | Tasker |
|------|---------|--------|
| **swarm-coding** | 解决「多代理如何并行」 | 解决「单代理如何不偷懒」 |
| **deep-research** | 解决「多源如何交叉验证」 | 解决「单步如何验证到位」 |
| **batch-download** | 解决「批量任务如何分解」 | 解决「单任务如何闭环」 |
| **cron** | 解决「定时触发」 | 解决「执行质量」 |

**核心优势**：Tasker 是**所有技能的基础设施**——它不替代任何技能，但让任何技能执行得更可靠。

## 三、应用范围

### 适用场景（7 大类）

1. **开发调试** — 修复 bug、实现功能、代码重构
2. **运维排障** — 查日志、诊断故障、配置修复
3. **研究分析** — 数据调研、竞品分析、根因定位
4. **写作输出** — 技术文档、报告、方案撰写
5. **规划审查** — 代码评审、方案评审、安全检查
6. **快速任务** — `/tasker` 轻量入口，快速执行小任务
7. **用户不满处理** — 投诉响应、纠错、信任恢复

### 适用平台

- OpenClaw / Clawdbot
- Kimi Work
- Claude Code / Cursor / Codex（任何遵循 Agent Skill 标准的平台）

## 四、能解决什么问题？

### 痛点 1：代理「说做了但没做」（幻觉/模拟）
**Tasker 解法**：
- Zero-Tool Zero-Progress Rule：没工具调用 = 没执行
- Pre-Tool Completion Ban：工具返回前禁止说"已完成"
- 每条执行必须有可验证产物（文件内容、stdout、日志）

### 痛点 2：代理「改坏了不知道」（缺少验证）
**Tasker 解法**：
- Post-Tool Verification（PTV）：写后立即读取确认
- Tool-Call Audit：verify 阶段必须列出所有工具调用及其效果
- 效果不覆盖 done_definition → 禁止进入 close

### 痛点 3：代理「死循环/超时」（无时间控制）
**Tasker 解法**：
- S/M/L 三级时间预算（60s/300s/900s 单步超时）
- 总状态转换次数上限（3/8/15 轮）
- 超出预算 → 优雅关闭并建议分解

### 痛点 4：代理「重复犯同样错误」（无改进机制）
**Tasker 解法**：
- 不满分类：5 类（结果/过程/理解/沟通/性能错误）
- 根因标签：6 种（幻觉/漏读/误读/工具失败/需求模糊/逻辑漏洞）
- 同一会话同根因 2+ 次 → 后续任务自动应用对应防护

### 痛点 5：代理「小事放大/大事忽视」（风险分级不准）
**Tasker 解法**：
- 基础：关键词权重评分（query=1, fix=5, delete=10）
- 修正：Session 上下文（父任务级别、历史失败）+ Path（敏感目录）+ User（生产环境提及）
- "修改登录页颜色"从 L 修正为可管理级别
- "查看文件"指向 `/etc/passwd` 自动升级为 M

### 痛点 6：大任务超出单代理能力（无法升级）
**Tasker 解法**：
- 内置多代理交接协议：L 级任务自动建议 swarm-coding / batch-download / deep-research / cron
- 生成结构化 `tasker_handoff.md`，避免重复澄清
- 执行 3 次失败后：提供「手动指导/多代理/中止」三选项

---

## 五、一句话总结

> **Tasker = 让 AI 代理从「能做事」变成「把事做对、做闭环、可追溯、不重复犯错」。**

它不教你写什么，它确保你写的东西**真实存在、真正正确、真正完成**。

## 六、给听众的快速演示脚本（3 分钟版）

**开场（30s）**：
> "大家用过 AI 写代码吧？有没有遇到过 AI 说'已经修复了'，但代码根本没改？或者它声称查了文件，实际上那个文件根本不存在？Tasker 就是解决这个问题的。"

**核心演示（2min）**：
1. 展示 `/tasker` 入口 → 轻量握手
2. 展示 S/M/L 自动分级 → "修改登录页颜色" vs "删除生产数据库"
3. 展示执行规则 → 写文件后立即 ReadFile 验证（PTV）
4. 展示失败回退 → execute 失败 → 回退 plan → 重新设计

**收尾（30s）**：
> "Tasker 不替代任何工具，它给所有工具加了一层'执行纪律'。就像开车的安全带——平时感觉不到，关键时刻救你一命。"
